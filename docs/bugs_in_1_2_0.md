# Баги и недочёты, присутствующие в версии 1.2.0

Этот файл — реестр проблем, обнаруженных при разработке 1.3.0, которые ЕСТЬ
и в текущей 1.2.0. По договорённости с владельцем проекта правки в 1.2.0
вносятся ТОЛЬКО после явного разрешения. Здесь фиксация — не фикс.

Статусы: [FIXED-IN-1.3.0] / [OPEN]

---

## 1. Resume молча игнорирует смену конфигурации objective [OPEN в 1.2.0]

**Симптом.** Пользователь меняет набор скореров (например, добавляет capability
proxy или BenchmarkScore) и запускает пайплайн с существующим журналом Optuna
(`output/abliteration_study/checkpoints/<model>.jsonl`). Optuna 4.x при
`create_study(load_if_exists=True)` **молча возвращает существующий study со
старыми directions** (проверено экспериментально на 4.9.0 — ошибки нет).
Дальше objective возвращает другое число значений, чем ожидает study →
криптический крах посреди прогона (`The number of values ... did not match`)
или тихо некорректное поведение.

**Воспроизведение.** Прогнать модель с дефолтными скорерами (2 objective),
затем запустить с `--capability-proxy` не удаляя журнал.

**Правильное поведение.** Явная ошибка с объяснением: журнал создан с другими
objective; удалить журнал или вернуть прежнюю конфигурацию скореров.

**Статус в 1.3.0:** [FIXED-IN-1.3.0] — guard после create_study сравнивает
directions и выдаёт понятную ошибку.

## 2. `n_startup_trials = trials // 3` сжигает ~треть бюджета [OPEN в 1.2.0]

Multivariate-TPE начинает моделировать после пары десятков наблюдений;
66 случайных стартовых трейлов из 200 — потраченное впустую время.
**Статус в 1.3.0:** [FIXED-IN-1.3.0] — `min(20, max(8, n // 8))` + флаг
`--startup-trials`.

## 3. Нет механизма раннего отброса заведомо доминированных трейлов [OPEN в 1.2.0]

Каждый трейл оплачивает полную оценку (генерация 100×100 токенов ≈ 26× дороже
KL-форварда). Замер на tiny-модели: отсев после KL-шага экономит ~96%
стоимости оценки мёртвого трейла. См. docs/optimization_ideas.md.
**Статус в 1.3.0:** [FIXED-IN-1.3.0] — multi-fidelity прунинг.

## 4. `max_response_length` жёстко 100 и недоступен из CLI/Settings [OPEN в 1.2.0]

Маркеры отказа появляются в первых ~20–40 токенах; хвост генерации — пустая
работа. Замер: 64 токена = 67% стоимости от 100.
**Статус в 1.3.0:** [FIXED-IN-1.3.0] — `--max-response-length`, дефолт 64.

## 5. Верхняя граница `max_weight` жёстко 1.5 [OPEN в 1.2.0]

Для attention-only прогонов attention один несёт всю абляцию и упирается в
потолок 1.5 — часть недостижимых отказов. **Статус в 1.3.0:**
[FIXED-IN-1.3.0] — `--max-weight-limit`.

## 6. Направление только из среднего residual-векторов [OPEN в 1.2.0]

На слоях с massive activations (у Qwen3.5-0.8B на последнем слое |r|≈102)
среднее искажается; покомпонентная медиана робастнее. **Статус в 1.3.0:**
[FIXED-IN-1.3.0] — `--direction-source median`.

## 7. Мёртвый код (косметика) [OPEN в 1.2.0]

- `native/config.py`: переменная `n_startup` присваивается и не используется.
- `native/model.py`: `subspace_k` в `abliterate()` не используется.
- `native/abliterator.py`: `finished` в блоке resume не используется; весь
  блок `if existing is not None:` пустой по смыслу.
- `native/abliterator.py`: `evaluator.base_capability = ...` — атрибут никто
  не читает.
- `pipeline.py`: в `_run_or_load_abliteration` ветка `backend="auto"` логирует
  «Falling back to Abliteration backend», но следующим оператором всегда
  кидает RuntimeError — сообщение недостижимо.

**Статус в 1.3.0:** [FIXED-IN-1.3.0] — весь мёртвый код удалён; пустой блок
resume заменён полезным предупреждением о продолжении завершённого study
(переменная `n_startup` исчезла при переписывании блока стартовых трейлов).

## 8. `base_refusals = 0` при кастомном наборе скореров [OPEN в 1.2.0]

Если в конфиге нет keyword-rate-подобного скорера, `NativeAbliteratorResult.
initial_refusals/final_refusals` заполняются нулями — сводка/отчёты показывают
некорректные числа. Ограничение архитектуры legacy-бриджа.

**Статус в 1.3.0:** [FIXED-IN-1.3.0] — сквозная семантика «не измерялось»:
поля refusals/total_prompts/kl_divergence стали Optional (в JSON — null),
отчёты (CSV/HTML/текст), консольная сводка и reproduce-метрики рендерят
**n/a** вместо фальшивых нулей; в логе печатается явное предупреждение.
Старое поведение для измеренного нулевого baseline (percent = 0.0) сохранено.
Тесты: tests/test_na_metrics.py + обновлённые test_comparison.py.

## 9. `--info` показывает захардкоженную версию 1.0.0 [OPEN в 1.2.0]

`src/anlord/__init__.py` несёт `__version__ = "1.0.0"` с давних времён; вывод
`--info` (строка `Abliteration:`) читает именно его, поэтому даже на
установленном с PyPI пакете 1.2.0.post1 выводится «1.0.0». Косметика,
но сбивает с толку при диагностике.

**Статус в 1.3.0:** [FIXED-IN-1.3.0] — `__version__` динамический: в
wheel-установке читается из метаданий pip-пакета (всегда совпадает с
установленным), в source-прогоне — константа релиза, синхронизируемая с
pyproject. Тесты: tests/test_version.py.

## Исправлено в 1.2.0 в ходе этой сессии (для истории, не требует действий)

- Фантомная critical-таблица несовпадений воспроизведения (ключ пакета,
  случайный суффикс unknown-версии, мусорный egg-info).
- Пустая сводка refusals/KL при воспроизведении (метрики в бандле).
- Восстановление display-флагов из бандла + недетерминизм пути направлений.
- Двойной лог batch size.
- MAX_PATH-падение имени журнала Optuna на длинных путях модели.
- Игнорирование явных CLI-аргументов в интерактивном режиме.
- ImportError скореров при запуске `python -m src.anlord`.
